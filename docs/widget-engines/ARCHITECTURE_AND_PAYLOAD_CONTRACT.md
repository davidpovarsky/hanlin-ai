# Widget execution and payload contract

## Current execution ownership

Prepared ScriptWidget execution uses one caller-owned cancellation control with an optional monotonic deadline. A missing deadline means no imposed application invocation deadline; it is not represented by an infinite duration or an oversized numeric value. A selected deadline delivers cancellation independently of the JavaScript callback queue, so instrumented synchronous JavaScript can observe it before the completion waiter begins.

The control follows timeline preparation, widget/control actions, native presentations and Live Activity preparation. Existing Swift task cancellation and view replacement/disappearance are forwarded to the execution owner. No additional WidgetKit or ActivityKit expiration callback or duration is assumed. Completion waiting, component resolution and frozen-value traversal observe the same cancellation state. Registered network tasks and provider handles are cancelled, completion waiters wake, and the JavaScript callback queue drains before the execution owner returns.

HTTP(S) transport preserves its original Promise/result shapes, endpoint and credential semantics, and package declarations. It adds no fixed request-count, request-body or response-body ceiling. Caller-supplied finite positive request timeouts are independent of the optional execution deadline; otherwise the normal transport defaults apply. Local and private HTTP(S) hosts are supported. The original-source manifest records each adaptation so upstream refresh can merge it explicitly.

These are source contracts. Native execution evidence must be tied to the source and SDK that actually ran. The following Pass 3 design and dated results are preserved as historical observations, including its former fixed deadlines and transfer limits; they are not current acceptance evidence. Current generated API and package contracts are linked from [the source inventory](SOURCE_AND_ABI_INVENTORY.md).

## Historical Pass 3 widget pipeline

The registered kind remains com.hanlin.scripting.widget in HanlinScriptingWidgets.appex. Three engines are selected by validated stored metadata: legacy, expo, scriptwidget. Missing engine in a historical v1 record means legacy; unknown declarations fail import. Corrupt v2 engine/payload records render an error.

Install Preview and installation use HanlinWidgetCompiler with explicit ABI/source-format metadata. Babel is the pinned ScriptWidget support resource. Expo JSX imports resolve to the pinned Expo Widgets globals; ScriptWidget JSX uses the original ScriptWidget.createElement/$element JSExport object and $render lifecycle. The generic Scripting compiler remains separate.

Installed programs are immutable HanlinWidgetProgram values: ABI, engine/upstream commit, source/compiler SHA, compiled source, action declarations, families and bounded resources. Host publication exports a generation-scoped content-addressed App Group ref. Descriptor inline source fields are empty for new native programs and are never a fallback authority.

The provider verifies the artifact and exact selected entity, executes a one-shot JSC context on its preparation task under the shared transaction, freezes a Sendable value, and supplies it to the timeline entry. ScriptWidget storage writes during preparation commit a state revision before returning; read-only preparation does not rewrite the snapshot. SwiftUI bodies render native prepared data and never compile or execute JavaScript. Expo's original AnyChild renderer lives in HanlinExpoWidgetNative under the existing binary-target owner. The WidgetKit target and its focused iOS renderer test target link this product. Its sole native dependency is the separate source-built HanlinExpoWidgetSubset, which excludes the foreground React/Hermes binaries. Both source modules compiled/linked with extension enforcement in 41239669157. The final built appex closure audit and SpringBoard assertions remain pending. ScriptWidget uses its original native builders/attributes with a narrow Hanlin resource/action context.

Identity includes installed package, package, generation, entrypoint, engine and a real configured variant. Family and artifact digest travel with the action context. The app can create independent named instances; identical selections share state. Exact recorded entity migrations follow upgrades; normal lookup never uses a partial identifier or first-widget fallback.

Native Button/Toggle -> typed command -> current enabled published installation and declared action -> verified program -> source callback/named function or Boolean set-value -> serialized atomic state revision -> reload only the registered kind. Legacy compiled intents keep their existing route. No hardcoded counter actions or UserDefaults fallback exists in the native router.

Host update/rollback/disable/uninstall invalidates extension action authority before asynchronous installed-store changes. Publication reads the latest state/instances under the same cross-process lock as actions and preserves Live Activities. User state is generation-scoped; upgrades keep variant IDs but start new generation state. Rollback to a retained generation restores its state. Uninstall removes its registry/state after installed-store removal.

No public JavaScriptCore API used here can preempt every native parser or built-in call. Compiler-inserted loop/function guards and pre/post deadlines are cooperative bounds, with explicit byte/tree limits. Native per-tap OS retry IDs are unavailable: generated invocation IDs distinguish real invocations; explicitly supplied nonces deduplicate the last 128 committed receipts. Automatic OS retries are at-least-once and are not advertised as exactly-once.
